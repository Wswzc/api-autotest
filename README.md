# 接口自动化测试框架

基于 **pytest + requests** 的分层接口自动化框架，覆盖多环境配置、yaml 数据驱动、
分层断言、并行执行、Allure 报告与 GitHub Actions 每日定时回归。

仓库自带一个用 FastAPI 实现的被测服务，因此 clone 下来**一条命令即可跑通全部用例**，
不依赖任何外部环境。

| 指标 | 当前值 |
| --- | --- |
| 用例总数 | **99** |
| 冒烟用例（门禁） | 24 |
| 优先级分布 | P0 50 / P1 40 / P2 9 |
| 安全专项 | 36 |
| 串行执行耗时 | 约 6 秒 |
| 并行执行耗时（-n 4） | 约 4.5 秒 |
| 并行安全性 | 已验证 -n 4 / -n 8 反复执行结果稳定 |

---

## 一、快速开始

```bash
pip install -r requirements.txt

# 跑全量用例（自动拉起被测服务）
pytest

# 或使用统一入口
python run.py                          # 本地环境全量
python run.py --mark smoke             # 只跑冒烟（提测准入）
python run.py -n 4 --report            # 并行 4 进程并生成 Allure 报告
python run.py --env test               # 切换到测试环境

# 查看报告（需本地安装 allure 命令行）
allure serve allure-results
```

## 二、目录结构与分层职责

```
api-autotest/
├── config/                  ① 配置层：多环境地址、账号、超时、阈值
│   ├── config.yaml
│   └── settings.py
├── common/                  ② 基础封装层：与业务无关的公共能力
│   ├── request_client.py       统一请求（重试/超时/日志/Allure 附件）
│   ├── assertions.py           分层断言
│   ├── yaml_util.py            数据加载与参数化转换
│   ├── data_faker.py           唯一数据生成与边界语料
│   └── logger.py               日志
├── apis/                    ③ 接口对象层：一个接口一个方法
│   ├── user_api.py
│   └── order_api.py
├── data/                    ④ 数据层：用例数据外置，与代码解耦
│   ├── user/login.yaml
│   ├── user/create_invalid.yaml
│   └── order/create.yaml
├── testcases/               ⑤ 用例层：只表达业务意图与断言
│   ├── test_login.py
│   ├── test_user_crud.py
│   ├── test_order.py
│   └── test_security.py
├── mock_server/             被测服务（FastAPI 实现）
├── conftest.py              全局 fixture 与会话生命周期
├── pytest.ini               pytest 与标记配置
├── run.py                   统一执行入口
└── .github/workflows/ci.yml CI 流水线
```

**分层的目的是让变更只影响一层**：接口路径变了只改 `apis/`，环境变了只改 `config/`，
测试数据变了只改 `data/`，用例层几乎不用动。

## 三、核心设计决策（这一节是框架的重点）

### 1. 分层断言：避免不稳定字段造成误报

第一版用"全量比对响应体"做断言，结果时间戳、自增 ID、token 这类天然变动的字段
造成大量误报。报告一红就没人看，自动化随即失去意义。

现在拆成六层，每层只断言真正应该稳定的东西：

| 层次 | 断言方法 | 说明 |
| --- | --- | --- |
| 传输层 | `Assert.status` | HTTP 状态码 |
| 业务层 | `Assert.code` / `msg_contains` | 响应体内的业务码与提示语 |
| 数据层 | `Assert.json_path` / `list_length` | 用 JSONPath 精确定位关键字段 |
| 结构层 | `Assert.schema` / `field_type` / `has_fields` | 值会变的字段只校验类型 |
| 安全层 | `Assert.no_sensitive_fields` | 密码、密钥等绝不能出现在响应里 |
| 性能层 | `Assert.response_time` | 单接口时延红线，阈值来自配置 |

所有断言失败信息都会带上**完整响应体**，避免为了看一眼响应而重跑用例。

### 2. 会话级 token：不让登录变成噪音

登录用 `scope="session"` 的 fixture 管理，整份用例集只登录一次。
用例数量到几百条时，这一项能省掉大量无意义的请求与执行时间。

同时准备了第二个账号的 token（`token_b`），专门用于水平越权测试。

### 3. 用例依赖走 fixture 链，不靠执行顺序

`token → client → api → 业务数据（created_user / pending_order / exclusive_sku）`
逐层依赖注入。pytest 会自动按依赖关系准备前置数据。

**不使用 `pytest-ordering` 之类的顺序控制**，因为顺序依赖一旦开启并行执行就会崩，
而 fixture 依赖不会。

### 4. 数据隔离：让并行执行真正安全

- 有唯一约束的字段（用户名、邮箱）全部带时间戳加随机后缀，用例自建自清
- 需要精确断言"库存减少了几件"的用例，通过 `exclusive_sku` fixture 申请**专属 SKU**
- 共享基础数据备足量，不会被用例累计耗尽

### 5. 服务生命周期放在会话入口，而不是 fixture 里

被测服务的启动与关闭放在 `pytest_configure` / `pytest_unconfigure`，
并通过 `hasattr(config, "workerinput")` 区分 xdist 的主进程与 worker。
原因见下方踩坑记录第 2 条。

## 四、踩过的坑与修复（真实过程记录）

这三个问题都是在本地跑通过程中真实暴露的，也是接口自动化最典型的三类"框架自身缺陷"。
它们的共同特征是：**看起来像产品 bug，实际是框架问题**——这类问题最消耗排查时间。

### 坑 1：共享资源被用例累计耗尽，导致后执行的用例随机失败

**现象**：串行第一次跑全绿，换个执行顺序或增加用例后，后半部分订单用例突然报"库存不足"。

**根因**：`SKU-001` 初始库存只有 10 件，而多条用例都会下单，其中支付成功的订单不会归还库存。
库存被逐渐耗尽后，后执行的用例就会失败——**而失败原因显示的是业务错误码，很容易被误判成产品缺陷**。

**修复（两条一起做）**：
1. 断言从"绝对值"改为"相对差值"，只校验本次操作带来的变化量
2. 需要精确断言库存的用例改用**专属 SKU**（`exclusive_sku` fixture），做资源隔离
3. 共享 SKU 备足库存，并保留一个固定为 0 的 SKU 专门验证库存不足的拒绝逻辑

### 坑 2：并行执行时，先跑完的 worker 把被测服务关掉了

**现象**：串行全绿，`-n 4` 并行时随机有一批用例失败，且每次失败的用例都不一样。

**根因**：服务启停原本写在 `scope="session"` 的 fixture 里。xdist 的每个 worker 都是
**独立进程**，都会执行一遍 session fixture——先跑完的 worker 在 teardown 阶段
把服务关了，其他 worker 剩下的用例全部连接失败。

**修复**：把服务生命周期上提到会话入口（`pytest_configure` / `pytest_unconfigure`），
并用 `workerinput` 属性区分主进程与 worker，只由主进程负责启停。

顺带修掉同一类问题：`--clean-alluredir` 在并行下会让每个 worker 都清一次报告目录，
互相删掉对方已写入的结果，因此在 worker 进程中强制关闭该选项。

### 坑 3：Windows 上进程树未被终止，旧服务残留占用端口

**现象**：修改了被测服务的代码，重跑用例却完全没生效，行为还是老的。

**根因**：`process.terminate()` 只终止直接子进程，服务往下派生的工作进程会残留并继续
占用端口。下一轮执行时端口探测发现"服务已在运行"，于是连到了**上一次的旧进程**，
跑的是旧代码和旧数据。

**修复**：Windows 上改用 `taskkill /F /T` 终止整个进程树，POSIX 上走 terminate；
并在 teardown 中确认进程确实退出。

## 五、用例设计说明

用例不是随手写的，覆盖维度对应具体的设计方法：

| 模块 | 用例数 | 主要设计方法与覆盖点 |
| --- | --- | --- |
| 登录 `test_login.py` | 16 | 等价类与边界值（空值、纯空格、超长、大小写、前后空格）、错误推测（SQL 注入 / XSS 字符）、账号锁定阈值、登出后 token 失效、响应结构与敏感字段 |
| 用户管理 `test_user_crud.py` | 27 | 增删改查全链路、**边界值取上下界及其 ±1**、唯一约束冲突、类型错误、分页边界（含页码 0 与超范围）、删除后再查与重复删除 |
| 订单 `test_order.py` | 22 | **状态迁移法**覆盖合法路径与全部非法迁移、**幂等性**（同键不重复扣减）、库存一致性、金额精度与四舍五入 |
| 安全 `test_security.py` | 34 | 认证缺失、凭证伪造（6 种畸形 token）、**水平越权**、**垂直越权**、恶意输入不得返回 5xx、敏感字段泄露 |

几个刻意的设计取向：

- **金额用字符串传入**：避免浮点在序列化环节先丢精度，这是支付类接口的高发缺陷区
- **越权测试是接口测试独有的价值**：前端不会渲染这些入口，UI 测试无法覆盖
- **恶意输入的核心断言是"绝不能返回 5xx"**：被 4xx 拦下是正确表现，出现 500
  说明输入直达底层，是明确的安全信号
- **登录失败不区分"账号不存在"与"密码错误"**：防止账号枚举，用例专门验证这一点

## 六、CI 流水线

`.github/workflows/ci.yml` 分两个作业：

| 作业 | 触发 | 作用 |
| --- | --- | --- |
| **冒烟门禁** | 每次 push / PR | 只跑 24 条冒烟用例，失败即阻止合并 |
| **全量回归** | 门禁通过后 / 每日凌晨 2 点 / 手动 | 并行跑全量，产出 Allure 报告并发布到 GitHub Pages |

设计要点：

- **门禁与回归分离**：门禁必须快（秒级），否则开发不愿意等；全量回归放到定时任务
- 日志与 Allure 原始结果都归档为 artifact，便于事后排查"昨晚为什么红了"
- 保留历史报告数据，Allure 能展示**通过率趋势**而不只是单次结果
- 回归失败会让流水线以非 0 退出码结束，不做静默通过
